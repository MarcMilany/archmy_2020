Jobber поддерживает таблицу заданий, в которой отслеживаются существующие задания и их текущий статус. При первоначальном запуске задания в таблицу заданий вносится запись. После запуска и последующего завершения задания в таблице заданий фиксируется его окончательное состояние (выполнено или прервано, а также статус завершения в случае выполнения). На этом этапе становится возможным удалить задание из таблицы заданий. Удаление задания — это инициируемая пользователем операция, в результате которой завершённое задание удаляется из таблицы заданий. В таблице заданий ограниченное количество записей, поэтому при удалении завершённых заданий освобождаются записи, которые могут быть использованы для новых заданий.

Интерфейс командной строки
При запуске jobber должен предоставить пользователю интерфейс командной строки со следующим запросом

работник>
Это сообщение должно быть выведено в stdout, как и любой другой вывод (идентификаторы заданий, сообщения об ошибках, строки состояния заданий, и т. д.), указанный ниже.

Ввод пустой строки после запроса should должен просто привести к повторению запроса без какой-либо другой распечатки или действия со стороны программы. Непустые строки интерпретируются как команды, подлежащие выполнению. Jobberкоманды имеют простой синтаксис, в котором каждая команда состоит из последовательности "слов" (которые, за исключением эффекта одинарных кавычек - см. Ниже) представляют собой последовательности символов, не содержащих пробелов, разделенных последовательностями из одного или нескольких символов-пробелов. Первое слово каждой команды - это ключевое слово, которое дает название команде. Все оставшиеся слова являются аргументами команды. Ваша реализация jobber должна поддерживать следующие команды с указанными аргументами.

Разные команды

help
quit
Информационные команды

status job_number ( номер задания )
jobs
Команды системного управления

enable
disable
Команды буферизации

spool задача
pause job_number ( номер задания )
resume job_number ( номер задания )
cancel job_number ( номер задания )
expunge job_number ( номер задания )
Команда help не принимает аргументов и в ответ выводит сообщение со списком всех типов команд, распознаваемых программой, например такое:

jobber> help
Available commands:
help (0 args) Print this help message
quit (0 args) Quit the program
enable (0 args) Allow jobs to start
disable (0 args) Prevent jobs from starting
spool (1 args) Spool a new job
pause (1 args) Pause a running job
resume (1 args) Resume a paused job
cancel (1 args) Cancel an unfinished job
expunge (1 args) Expunge a finished job
status (1 args) Print the status of a job
jobs (0 args) Print the status of all jobs
jobber> 
Команда quit не принимает аргументов и завершает выполнение. Перед завершением программа должна отменить все задания, которые не были завершены. Она должна дождаться завершения всех заданий, а затем удалить все задания из таблицы заданий, чтобы освободить память, которую они использовали. Наконец, программа завершает работу со статусом EXIT_SUCCESS.

Команда enable устанавливает флаг, разрешающий запуск отложенных заданий, и немедленно запускает все отложенные задания, которые не были запущены, до достижения ограничения на максимальное количество заданий, которые могут быть активны одновременно. Обратите внимание, что изначально запуск заданий не разрешён.

Команда disable сбрасывает флаг, разрешающий запуск отложенных заданий. Задания не будут запускаться до тех пор, пока не будет выполнена команда enable .

Команда spool запускает новое задание. Например:

spool 'echo start ; cat /etc/passwd | grep bash > out ; echo done'
Здесь одинарные кавычки (') используются для того, чтобы рассматривать как одно слово то, что в противном случае интерпретировалось бы как несколько слов. Таким образом, приведённая выше команда состоит всего из двух слов: spool и echo start; cat /etc/passwd | grep bash > out ; echo done. Обратите внимание, что сами кавычки не становятся частью слова. Второе слово в команде spool указывает на задачу, которую должна выполнить работа. Команда spool назначает новому заданию слот в таблице заданий и отвечает пользователю выводом одной строки, содержащей идентификатор задания только что созданного задания. Идентификатор задания — это целочисленный индекс слота в таблице заданий, назначенного заданию. Он используется для идентификации задания в других командах. Если доступных слотов для заданий нет, задание не создаётся и пользователю сообщается об ошибке.

Команда pause приостанавливает выполнение задания (указанного по его идентификатору). Приостановка задания осуществляется путем отправки сигнала SIGSTOP в группу процессов исполнителя задания. Если указанный идентификатор задания не является идентификатором существующего задания или задание в данный момент не выполняется, пользователю сообщается об ошибке.

Команда resume возобновляет выполнение приостановленного задания (указанного по его идентификатору). Возобновление задания осуществляется путем отправки сигнала SIGCONT в группу процессов исполнителя задания. Если указанный идентификатор задания не является идентификатором существующего задания или задание в данный момент не приостановлено, пользователю сообщается об ошибке.

Команда cancel помечает задание (указанное по его идентификатору) как «отменённое» и пытается принудительно завершить его. Если задание ещё не запущено, оно просто не может быть запущено. Если задание уже запущено, оно завершается путём отправки сигнала SIGKILL группе процессов задания. Если указанный идентификатор задания не является идентификатором существующего задания или задание уже завершено, его нельзя отменить и пользователю будет сообщено об ошибке.

Команда expunge удаляет завершённое задание (указанное по его идентификатору) из таблицы заданий. Если указанный идентификатор задания не является идентификатором существующего задания или задание ещё не завершено, пользователю сообщается об ошибке.

Команда status выводит текущий статус задания (указанного по его идентификатору); например:

jobber> status 3
job 3 [waiting]: echo start ; cat /etc/passwd | grep bash > out ; echo done
jobber>
Здесь в выводе отображается номер задания, его текущий статус (подробнее о статусах заданий чуть позже) и описание задачи. Если задание выполнено, будет также показан его статус завершения; например:

jobber> status 3
job 3 [completed (0)]: echo start ; cat /etc/passwd | grep bash > out ; echo done
jobber>
Если указанный идентификатор задания не соответствует идентификатору существующего задания, пользователю сообщается об ошибке.

Команда jobs выводит отчёт о текущем состоянии всех существующих заданий в таблице заданий. Например:

job 1 [aborted]: foo
job 2 [completed (0)]: sleep 30
job 3 [waiting]: echo start; cat /etc/passwd | grep bash > out ; echo done
Статус задания
Состояние задания будет одним из следующих: NEW, WAITING, RUNNING, PAUSED CANCELED, COMPLETED ABORTED,,,,,,,,,,,,,,,. Переходы между этими состояниями происходят по следующим правилам:

Новое задание начинается с состояния NEW .
После полной инициализации нового задания оно переходит в состояние WAITING.
Задаче WAITING может быть назначен процесс-исполнитель, и она может быть переведена в состояние RUNNING. Это возможно, если текущее количество исполнителей меньше MAX_RUNNERS.
Пользователь может приостановить задание RUNNING , в этом случае статус задания изменится на PAUSED, а группе процессов исполнителя будет отправлен сигнал SIGSTOP .
Пользователь может выбрать возобновление PAUSED задания, в этом случае статус задания устанавливается в RUNNING и группе процессов исполнителя отправляется SIGCONT сигнал.
Задание, задача которого выполнена успешно, переходит в состояние COMPLETED.
Задание, выполнение которого завершается сигналом, переводится в состояние ABORTED.
Пользователь может отменить задание, находящееся в любом состоянии, кроме CANCELED, COMPLETED, или ABORTED. Если задание ещё не запущено, его статус просто меняется на ABORTED. Если задание уже запущено, его статус меняется на CANCELED и группе процессов исполнителя (если задание уже запущено) отправляется сигнал SIGKILL. Когда задание завершается, его состояние меняется с CANCELED на COMPLETED или ABORTED в зависимости от того, как произошло завершение. Обратите внимание, что отменённое задание всё равно может оказаться в состоянии COMPLETED, если оно было выполнено сразу после того, как его состояние было изменено на CANCELED, но до того, как SIGKILL было передано в группу процессов исполнителя задания.
Обратите внимание, что задание можно удалить только в том случае, если оно находится в состоянии COMPLETED или ABORTED .

Обработка сигналов
Программа jobber должна установить SIGCHLD-обработчик, чтобы получать уведомления сразу после завершения процесса выполнения задания. -обработчик должен соответствующим образом обновлять информацию о статусе задания и запускать все последующие задания в таблице заданий, которые теперь можно обработать, поскольку существующий процесс выполнения задания завершился.

:nerd: Обратите внимание, что вам нужно будет использовать sigprocmask() для блокировки сигналов в нужный момент, чтобы избежать гонок между обработчиком и основной программой, которые могут привести к неопределённому поведению.

Установленный вами обработчик должен быть безопасным для асинхронных сигналов. Ниже приведены некоторые технические сведения о том, как правильно реализовать обработчик.

Считывание входных данных
Когда процесс считывает вводимые пользователем данные, ему обычно приходится блокироваться (ждать), пока вводные данные не станут доступны. Если во время блокировки процесса поступает сигнал, то read() системный вызов прерывается, запускается любой обработчик, установленный для этого сигнала, а затем read() вызов возвращается с «коротким счётчиком». Всё это хорошо, пока обработчик сигнала может позаботиться обо всём, что нужно сделать в связи с поступившим сигналом. Однако, поскольку вызывать многие полезные функции внутри обработчика сигнала небезопасно, обработчик часто может сделать только одно: установить флаг, указывающий на то, что поступил сигнал, и организовать вызов отдельной функции для проверки флага и последующей обработки сигнала из контекста основной программы, когда обработчик вернётся и не будет ограничений на функции, которые можно безопасно вызывать. Однако возникает проблема: как и когда вызывать эту отдельную функцию. Мы бы хотели вызывать эту функцию перед блокировкой ввода данных пользователем, иначе обработка сигнала может быть отложена на неопределённый срок, пока пользователь не введёт данные. С другой стороны, если мы просто вызовем эту отдельную функцию непосредственно перед блокировкой ввода данных пользователем, всегда будет оставаться небольшой промежуток времени, в течение которого сигнал может прийти слишком поздно и не быть замеченным до блокировки. Этого состояния гонки можно было бы избежать, если бы мы маскировали сигналы, вызывали отдельную функцию для обработки уже поступивших сигналов, а затем блокировали бы ввод данных пользователем, но мы не можем этого сделать, потому что тогда сигналы будут маскироваться на всё время, пока процесс ожидает ввода данных пользователем, и программа снова не сможет оперативно реагировать на сигналы. Нам нужно иметь возможность маскировать сигналы, обрабатывать уже поступившие сигналы, а затем атомарно снимать маскировку с сигналов и блокировать ввод данных. Системный вызов pselect() («выбор POSIX») предоставляет такую возможность. Однако даже при использовании pselect() написать корректную, не подверженную конфликтам функцию, которая может принимать пользовательский ввод и при этом оперативно реагировать на сигналы, довольно сложно, поэтому я предоставил вам такую функцию под названием sf_readline().

Вы должны использовать предоставленную функцию sf_readline() для получения данных от пользователя. Интерфейс этой функции по сути является упрощенной версией функции readline() в GNU, но вы не должны использовать GNU readline(), поскольку реализация этой функции не обеспечивает корректную обработку сигналов без гонок и безопасно. Функция sf_readline() вызывает указанную вами функцию-обработчик для обработки сигналов непосредственно перед блокировкой в ожидании ввода данных пользователем. Функция-обработчик должна быть указана во время инициализации программы путем вызова функции sf_set_readline_signal_hook() и передачи функции-обработчика в качестве параметра. Блокировка в sf_readline() осуществляется с помощью pselect(), как описано выше, чтобы исключить короткий промежуток времени, в течение которого сигнал может поступить, но не будет обработан до тех пор, пока пользователь не введёт данные. Ваши фактические обработчики сигналов (установленные с помощью signal() или sigaction()) должны быть функциями, безопасными для асинхронных сигналов, которые просто устанавливают флаг, указывающий на поступление сигнала. Фактическая обработка сигналов должна выполняться в отдельной функции-обработчике, которую вы реализуете и которая будет вызываться из sf_readline().

Анализ Спецификаций задачи
Одна из функций, которую должен выполнять jobber, — это преобразование спецификации задачи, введённой пользователем, в форму, которую может использовать процесс выполнения задачи. Хотя умение писать простые парсеры, подобные тому, который требуется здесь, является важным навыком, это не главная цель задания. По своему предыдущему опыту могу сказать, что студенты часто отвлекаются на это и не уделяют должного внимания важной части задания, а именно обработке процессов. По этой причине, а также из соображений единообразия при выполнении заданий, я предоставил функцию parse_task(), которую вы должны использовать для разбора спецификаций задач, введённых пользователем. Функция parse_task() — это простой рекурсивный анализатор, который принимает в качестве параметра указатель на переменную, содержащую (char *) указатель на строку спецификации, подлежащую анализу. Он пытается интерпретировать строку как спецификацию задачи и возвращает указатель на TASK структуру, представляющую задачу. Если он не может интерпретировать строку как TASK, возвращается NULL Обратите внимание, что parse_task() изменяет как передаваемую переменную, так и строку спецификации, на которую она указывает, поэтому необходимо создавать копии, если после вызова parse_task(). требуются неизменённые версии. Объект TASK, возвращаемый parse_task(), должен быть освобождён вызывающей стороной с помощью предоставленной функции free_task(), когда объект больше не нужен.

Выполнение задания
Чтобы выполнить задание, сначала нужно создать процесс runner для этого задания. Как уже говорилось выше, существует ограничение на количество процессов runner, которые могут существовать одновременно, поэтому любое задание может находиться в состоянии WAITING до тех пор, пока количество существующих runner не снизится до уровня ниже предельного. Задача процесса-исполнителя — выполнить задачу задания, организовав последовательное выполнение конвейеров, составляющих эту задачу, отслеживая (с помощью wait(2) или waitpid(2)) завершение или прерывание каждого конвейера, а затем либо завершая свою работу (с помощью exit(3)), либо прерывая её (с помощью abort(3)); в первом случае в качестве собственного статуса завершения используется статус завершения последнего конвейера. Процесс-исполнитель должен использовать setpgid(2) для создания новой группы процессов с идентификатором, равным его идентификатору процесса. Позже это позволит killpg(2) отправлять сигналы группе процессов, чтобы остановить, продолжить или завершить задачу. Основная программа должна использовать SIGCHLD сигналы, чтобы отслеживать завершение процессов-исполнителей, и waitpid(2) для их сбора.

Чтобы выполнить конвейер, процесс-исполнитель должен создать главный процесс конвейера для этого конвейера. Главный процесс конвейера создаст по одному дочернему процессу для каждой команды в конвейере, организовав таким образом, чтобы выходные данные каждой команды направлялись через канал (см. pipe(2) и dup(2)) на вход следующей команды в конвейере. Каждый командный процесс должен использовать execvp(3) для выполнения соответствующей команды. Кроме того, мастер конвейера настроит первую команду конвейера на получение входных данных из любого файла, указанного с помощью перенаправления ввода (см. open(2) и dup(2)), а также настроит последнюю команду конвейера на отправку выходных данных в любой файл, указанный с помощью перенаправления вывода. Если какой-либо командный процесс в конвейере прерывается (завершается с помощью сигнала), то считается, что весь конвейер прерван, и мастер конвейера сам прерывается (снова с помощью abort(3)). Любая ошибка при настройке самого конвейера также будет считаться причиной прерывания работы мастера конвейера. Если все командные процессы в конвейере завершаются (выходят из строя в штатном режиме), то считается, что весь конвейер завершён, и статус выхода последней команды в конвейере будет использоваться в качестве статуса выхода (с использованием exit(3)) мастера конвейера.

Важно: вы должны создавать процессы в задаче с помощью вызовов fork() и execvp(). Вы не должны использовать функцию system() или какую-либо оболочку для создания конвейера, так как цель задания — дать вам опыт использования системных вызовов, необходимых для этого.

Пакетный режим
Обычный режим работы jobber - это интерактивное приложение с командной строкой. Однако он также должен корректно работать в пакетном режиме, в котором стандартный ввод был перенаправлен из командного файла или даже из канала. Вам следует убедиться, что ваша программа действительно функционирует корректно таким образом, потому что мы будем использовать это либо для подачи вашей программе предопределенной последовательности команд, либо даже для запуска вашей программы параллельно с программой-драйвером, которая выдает команды и отслеживает происходящее, используя функции событий, описанные выше.

Функции, которые Вы Должны Реализовать
В рамках реализации jobber вы должны предоставить реализации следующих функций, более подробные спецификации которых приведены в jobber.h:

int jobs_init(void) — Инициализируйте буфер заданий.
void jobs_fini(void) — Завершите обработку заданий.
int jobs_set_enabled(int enabled) — Укажите, можно ли запускать задания.
int jobs_get_enabled(void) — Узнайте, можно ли запустить задания.
int job_create(char *task) — Создайте новое задание.
int job_expunge(int jobid) — Уволить с работы.
int job_cancel(int jobid) — Попытка отменить задание.
int job_pause(int jobid) — Приостановите выполняемое задание.
int job_resume(int jobid) — Возобновить приостановленное задание.
JOB_STATUS job_get_status(int jobid) — Получите информацию о текущем статусе задания.
int job_get_pgid(int jobid) — Получите идентификатор группы процессов, в которой выполняется задание.
int job_get_result(int jobid) — Получите результат (т. е. статус завершения) задания.
int job_was_canceled(int jobid) — Определите, была ли задача успешно отменена.
char *job_get_taskspec(int jobid) — Получите описание задачи.
Важно, чтобы вы в точности следовали приведённым спецификациям, потому что некоторые тесты, которые мы используем для выставления оценок, скорее всего, будут модульными тестами, напрямую вызывающими эти функции.

Функции событий, которые вы Должны Вызвать
Чтобы мы могли отслеживать действия вашей программы, мы предусмотрели несколько функций, которые вы должны вызывать в определённых ситуациях. Вот они:

void sf_job_create(int jobid); Вы должны вызывать эту функцию при создании нового задания, до того как его статус изменится с NEW. Аргументом является идентификатор нового задания.
void sf_job_expunge(int jobid); Вы должны вызвать эту функцию сразу после удаления задания. Аргументом является идентификатор удалённого задания.
void sf_job_status_change(int jobid, JOB_STATUS old, JOB_STATUS new); Вы должны вызывать эту функцию при каждом изменении статуса задания. Аргументами являются идентификатор задания, статус которого меняется, старый статус задания и новый статус.
void sf_job_start(int jobid, int pgid); Вы должны вызывать эту функцию, когда задание начинает выполняться. Аргументами являются идентификатор запускаемого задания и идентификатор группы процессов исполнителя, назначенного для выполнения задания.
void sf_job_end(int jobid, int pgid, int result); Вы должны вызывать эту функцию в момент завершения процесса-исполнителя. Аргументами являются идентификатор завершённого задания, идентификатор группы процессов исполнителя, назначенного для задания, и статус завершения процесса-исполнителя, возвращаемый waitpid().
sf_job_pause(int jobid, int pgid); Вы должны вызывать эту функцию, когда получение SIGCHLD сигнала указывает на то, что задание приостановлено. Аргументами являются идентификатор запускаемого задания и идентификатор группы процессов исполнителя, назначенного для выполнения задания.
sf_job_resume(int jobid, int pgid); Вы должны вызывать эту функцию, когда получение SIGCHLD сигнала указывает на возобновление задания. Аргументами являются идентификатор возобновляемого задания и идентификатор группы процессов исполнителя, назначенного для выполнения задания.
Вышеуказанные функции предоставляются вам в виде объектного файла, который будет связан с вашей программой. В базовом коде эти функции сообщают на stderr о том, что они были вызваны, чтобы вы могли убедиться, что вызываете их правильно. Если вы не хотите видеть эту надпись, вы можете присвоить глобальной переменной sf_suppress_chatter ненулевое значение. Когда мы будем оценивать вашу программу, мы заменим реализации этих функций в базовом коде на другие версии, которые позволят нам проверить, действительно ли события происходят в том порядке, в котором они должны происходить.

Раздаточные инструкции
Как обычно, перед отправкой убедитесь, что ваше домашнее задание компилируется. Тщательно протестируйте его, чтобы убедиться, что оно не приводит к сбоям или «нестабильному» поведению из-за состояния гонки. Используйте valgrind для проверки на наличие ошибок и утечек памяти. Помимо --leak-check=full, используйте опцию --track-fds=yes для проверки того, не происходит ли утечка файловых дескрипторов из-за того, что они не были должным образом закрыты. Возможно, вам также будет интересно изучить valgrind --trace-children и связанные с ним опции.
